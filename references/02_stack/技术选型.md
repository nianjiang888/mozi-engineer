# 技术选型

> 选技术不是选最酷的，是选**三个月后还能继续用**的。

## 选型四问

1. **要解决什么问题**：不是"用 React 还是 Vue"，是"我团队 3 人能 3 天搭出能上线的电商骨架吗"
2. **替换成本多大**：锁定的部分（数据、运维、人才、协议）vs 可换的部分（库、工具、内部框架）
3. **社区和寿命**：最近一次主版本发布是何时；bus factor 多少；license 是什么
4. **人才半径**：你团队 + 你招得到的人，懂这个的概率

## 选型矩阵（举例）

```
候选  |  解决当下  | 替换成本  | 社区寿命  | 团队熟悉
------|-----------|----------|-----------|--------
A     |   ✓✓✓       |   高       |   ✓✓✓      |   ✓
B     |   ✓✓        |   低       |   ✓✓       |   ✓✓✓
C     |   ✓         |   中       |   ✓         |   ✗
```

## 锁定 vs 可换的三层

| 层 | 建议 | 例子 |
|---|---|---|
| 锁定（难以替换）| 选最稳最通用 | DB（Postgres/MySQL）、主要语言、RPC 协议 |
| 可换（替换便宜）| 选最方便当下 | Web 框架、UI 库、ORM |
| 内部私有 | 选最小依赖 | 内部框架、CLI 工具、报表系统 |

## 框架/库的"红旗信号"

- 半年没新 commit、issue 堆 1000+
- 主版本变了 API 全废（breaking change）且没迁移路径
- Stars 多但 contributor 全是同一公司某一人
- 文档还是 v0.x 的写法，代码已 v5.x
- License 含 AGPL/SSPL 而你是闭源产品 → **直接不选**

## 选 ORM/DB 的最小判据

- 事务隔离：能否支持 repeatable read / serializable
- 连接池：能否测出耗尽边界
- 慢查询：能否方便定位（explain、pg_stat_statements 等）
- 备份：RPO/RTO 多少
- 上云：vendor lock 风险有多深

## 选前端框架的最小判据

- SSR/SSG 的取舍：SEO 重要不？CDN 友好不？
- bundle size 上限：3G 用户占比？低端机占比？
- 团队熟悉度 vs 招人难度
- 生态成熟度：UI 库、状态管理、表单库、动画库是否齐

## 决策记录（ADR）

每做一个不可逆决定，写 200 字的 ADR：

```
# ADR-007: 选用 Postgres 而非 MySQL

## 状态
2025-09-accepted

## 背景
订单系统用关系型 DB，社区中 MySQL 经验更多。

## 决策
用 Postgres 16。

## 取舍
- Postgres: jsonb 更顺、副本延迟更稳、扩展生态丰富
- MySQL: 团队熟悉度、招聘容易、运维经验丰富

## 后果
- 一次培训投入（团队 Postgres）
- 监控/dba 工具链替换
- 未来要换回 MySQL 成本 2-4 周
```

## 反模式

- "听群里 / stack overflow / reddit 哪个火选哪个"
- "老板让用 X，所以用 X" → 要么 override 决策，要么承认是约束
- "看到 benchmark 第一就选" → benchmark 测的是别人家的场景
