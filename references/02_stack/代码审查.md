# 代码审查

> 代码审查不是给作者找茬，是把"几个月后的自己 + 同事 + 攻击者"都带进房间。

## 审查的两个时段

- **写之前（设计 review）**：30 秒讲改动意图 + 取舍，省 90% 后续 review 时间
- **合之前（实现 review）**：照单子点，找 design review 没考虑到的地方

## 快速过 PR 的 90 秒清单

### 必须
- [ ] diff ≤ 400 行（超出请拆 PR）
- [ ] 有对应的任务单号 + Spec 链接
- [ ] 错误路径有错误信息（不是 `null`、`""`、`false`）
- [ ] 没有新增静态资源/依赖却没进 lockfile
- [ ] 数据库迁移有 down 脚本

### 建议
- [ ] 命名一眼能猜到用途
- [ ] 关键逻辑有注释解释**为什么**而不是**做什么**
- [ ] 失败/边界测试在 PR 里
- [ ] 没有复制粘贴 3 次以上的代码块（DRY）

### 不能要
- 调试 println / console.log 没删
- 注释里写 TODO/FIXME/Xxx 没跟 Issue

## 设计 review 必问的 3 个问题

1. **有没有更简单的方案**：砍掉 50% 代码同时保留 95% 价值？
2. **失败路径在哪**：能写出"出错时用户看到什么"？
3. **可逆性**：出问题能 30 秒回滚吗？

## 写 review 评论的语态

- ✅ "这里 `null` 返回会让调用方一直重试，建议改成 410 + reason"
- ❌ "这写的啥玩意？"

PR 评论是给作者 + 未来读者 + 公司资产看的，**不是吐槽**。

## 何时用 "Approve with comments"

- 不阻塞合并但需要后续清理
- 必须建 Issue 或同 PR 后面追加 commit

## 何时用 "Request changes"

- 会引入安全/数据/资金风险
- 设计意图不清，需要先讲清楚再写

## 审查者本人也要做的

- 24 小时内至少评论一次（PR 不可堆超 1 天没人看）
- 用建议语态，别用命令语态
- 关注 diff + 没改的文件，关注"调用方"和"测试"

## 反模式

- "LGTM" 刷赞 → 形同虚设
- 关注风格多于关注正确性 → format 让 linter 管
- 长 debate 走 PR 评论 → 转 Slack/会议，结论回 PR 一行
