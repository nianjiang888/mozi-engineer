# 代码生成

> AI 写代码 ≠ 不用管。AI 是杠杆，杠杆越粗，工程纪律要越细。

## 三阶生成（不要直接让 AI 写整个特性）

1. **脚手架**：AI 写文件结构、函数签名、注释骨架、Type/Interface
2. **核心逻辑**：人手写或逐函数生成；每 10 行停一次，读、留 commit
3. **测试 + 边界**：AI 帮忙生成测试，自己挑要保的边界

## 生成代码前的两件事

- 给出**清晰的输入输出**（接口契约、类型、错误码）
- 给出**至少 2 个示例**（happy path + edge case）

## 生成代码后的四件事

1. **读**：别立刻用，先 30 秒通读一遍，看是不是真的对
2. **运行**：跑示例；跑测试；看实际输出
3. **钉死**：哪些行为是"我已接受"的；commit 时写明
4. **观察**：合到主干后前 24 小时日志/告警重点看

## 模板项目（脚手架）的最小骨架

```
src/
  index.{ts|py|go}
  types/
  services/
    <feature>
      handler
      service
      repo
      schema
  lib/
  test/
config/
  default.yaml
  local.yaml (gitignore)
```

AI 写脚手架前给这套目录约定，比让它"随便放"省 50% 时间。

## 样板代码（boilerplate）哪些可以 AI 接管

| 让 AI 接管 | 必须人手写 |
|---|---|
| CRUD 模板 | 业务策略（状态机、配额、风控）|
| 测试 fixture | 复杂的领域规则 |
| 文档生成 | 算法选型（trade-off 决定）|
| 类型/接口 | 关键路径的安全审计（认证、支付）|

## 反模式

- "AI 写完我直接合并" → 没人审 = 没人负责
- "一次 prompt 让 AI 写完整个模块" → 输出越长，质量越指数级下降
- "AI 起的函数名直接用" → 函数名 = 设计，先读再决定
- "AI 写的测试就是真的" → AI 容易生成"伪测试"——只验 happy path
