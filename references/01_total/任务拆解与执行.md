# 任务拆解与执行

> 大任务不是写在脑子里，是写在一张可勾的清单上。

## 拆任务的三种粒度

| 粒度 | 时长上限 | 谁领 | 何处 |
|---|---|---|---|
| **Epic** | ≤ 2 周 | 负责人 | 文档/工作流 |
| **Task** | ≤ 2 人天 | 执行者 | 任务系统 |
| **Sub-task** | ≤ 0.5 人天 | 执行者 | PR/Commit message |

**关键**：粒度决定能见度。一个跨周的 Epic 是看不见的，跨天的 Task 是能看见的，跨小时的 Sub-task 是可控的。

## 拆法（WBS 的最小可用版）

每个 Task 明确写出 4 样东西：

1. **目标态**：做完是什么样？（可截图/可截图/可报表，最好有客观产物）
2. **依赖**：等谁？（API、组件、决策、环境）
3. **风险**：最坏情况是什么？（地雷在哪）
4. **验证**：怎么知道做好了？（验收条件/测试命令/可观测指标）

```
Task T-105: 实现订单创建接口
  目标态:  POST /v1/orders 能成功创建并返回 201 + order_id
  依赖:    T-103 (数据库迁移就位), T-104 (商品服务接口)
  风险:    防超卖逻辑可能漏；高并发下 ID 生成器成瓶颈
  验证:    1) 单测覆盖超卖/缺货/支付/状态机 4 种
           2) 集成测试覆盖完整下单流程
           3) k6 压测 p99 < 200ms
```

## 依赖图优先于甘特图

画一张依赖图（task A → B）胜过画一堆甘特条。 依赖图告诉你**并行能跑多宽**，甘特图只告诉你**截止日**。

## 排期的两个常见错觉

- **"我做完 = 上线"**：做完 = 验收通过 ≠ 已经生产稳定运行
- **"9 成功能 = 90% 进度"**：剩 10% 经常是 90% 工作量（边界、错误、运维、上线）

## 单人 vs 团队

| 多人协作 | 单兵 |
|---|---|
| 用任务系统的"待领取"队列 | 用 TODO 列表（甚至纸）|
| 公共 branch 命名约定 | `main` 直接推 |
| 必须有 PR + Review | 自审 + 跑测试 |

## 反模式（看见就跑）

- 大任务一礼拜没人拆 → 看不出阻塞
- 拆完没人认领 → 责任真空
- 任务之间耦合没画出来 → 临上线发现串行
- "修一下"的子任务 → 永远不会单独修
