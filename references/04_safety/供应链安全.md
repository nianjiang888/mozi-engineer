# 供应链与依赖安全

> 你用的每一个包都是别人的代码 + 别人的债 + 别人的漏洞。

## SBOM（软件物料清单）

让项目能输出一棵依赖树：

```
myapp 1.0
├── requests 2.31.0  (MIT)
│   ├── urllib3 2.0.7  (MIT)
│   └── charset-normalizer 3.2.0
├── authlib 1.2.1  (BSD-3)
└── openpyxl 3.1.2  (MIT)
```

工具：`syft`、`cyclonedx-bom`、`cdxgen`。

## License 合规的最小动作

| 许可证 | 闭源商用 | 备注 |
|---|---|---|
| MIT / BSD / Apache 2.0 | ✅ OK | 保留 LICENSE 即可 |
| ISC / Unlicense | ✅ OK | 同 MIT |
| MPL 2.0 | ⚠️ 看用法 | 修改的 MPL 文件需开源，调用 OK |
| LGPL | ⚠️ 看链接方式 | 动态链接 OK，静态链接要开源改动 |
| GPL v2/v3 | ❌ 传染 | 闭源产品禁用 |
| AGPL v3 / SSPL | ❌ 强传染 | **网络服务也强制开源** |
| BUSL / RPL | ⚠️ 自定义 | 商用需额外授权 |
| 商业 / Proprietary | ❌ 需购买 | 别忘了买 |
| "Unknown" / 双协议混淆 | ❌ 不用 | 高风险 |

## License 检测工具

- `license-checker`（npm）
- `pip-licenses`（pip）
- `cargo-license`（cargo）
- 每个 PR 必须过一遍

## 依赖攻击的常见套路

### 1. typosquatting（拼写陷阱）
官方 `requests` vs 依赖树里 `reqests`/`requestss`。`pip install requsts` 看着没毛病。

**防护**：
- 锁 lockfile
- CI 里加 "所有 import 必须来自 lockfile"

### 2. dependency confusion
内部私有包 `internal-utils` vs 公网同名包 `internal-utils`。攻击者把恶意版本推到公网，工具优先取公网版本。

**防护**：
- 私有 registry（如 Verdaccio/Nexus）
- 加 scope（如 `@yourorg/internal-utils`）

### 3. 维护者失守/投毒
node-ipc、event-stream、colors 等历史事件。
**防护**：
- SCA 扫描：`snyk`、`socket.dev`、`osv-scanner`
- 卡 version range：`~1.2.3` 不写 `^1.2` 不写 `latest`

### 4. transitive 漏洞
你的 `requests` 安全，`requests` 的 `urllib3` 有 CVE，被你的 build 包含。

**防护**：
- 工具：`npm audit`、`pip-audit`、`osv-scanner`、`snyk`
- 让 CI 失败：critical CVE 不许上

## 升级策略

| 升级类型 | 频率 | 测试强度 |
|---|---|---|
| patch (z) | 频繁 | 自动化 PR + CI |
| minor (y) | 季度 | 自动化 PR + E2E + oncall review |
| major (x) | 谨慎 | 单独分支 + 全文档评审 |

major 升级要写 ADR。

## 依赖的"减法"

- 业务能用 stdlib 就别加包
- 半年没人用 = 删（不删会跟着 CVE 死灰复燃）

## 反模式

- "我装的是最新版本" → 最新 ≠ 安全，可能是新发的不稳
- "我没用所以不担心" → 间接依赖照样进 build
- "装完跑跑就行" → 装完 = 看 SBOM + license + 漏洞 + 锁版本
- "我们自己写的" → 自己的代码也可能有 CVE 模式，复用成熟库常常更稳
