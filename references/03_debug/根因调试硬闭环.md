# 根因调试硬闭环

> 修 bug 不写 RCA = 给下一个当接盘侠的机会。根因不锁定，下次换个路口还会爆。

## 五问 Five Whys（不机械，照着思路走）

每问一次"为什么"，答案必须落到**机制/流程/设计/数据**层，而不是落到**人**。

```
症状    : 用户支付后没收到回调
为什么  : 商户侧没收到我们的 webhook
为什么  : 我们签名头校验失败
为什么  : 商户端用错了签名版本（v2 我们发了 v1）
为什么  : 商户 v1 代码被 fork 后没继续维护
为什么  : 我们没在文档强制标记"v1 已废弃,2026 移除"
```

根因 = 文档缺失**机制**层。修法 = 在 Spec/CI/文档加 "v1 is deprecated" 自动校验。

## 鱼骨图（Ishikawa）

围绕结果（"事故 P0 了"），分六支：

- **方法**：流程、文档、规范、Spec
- **机器**：硬件、网络、平台
- **测量**：监控、告警、采样
- **人力**：培训、值班、人手
- **材料**：依赖、第三方库、数据
- **环境**：配置、环境差异

六支都过一遍，命中哪支写哪支，不是凑数。

## 根因 vs 贡献因素

**贡献因素**：所有让事故"更容易发生"的事  
**根因**：去掉这一条事故就不会发生

写 RCA 时，**根因只能有一个**，其他都是贡献因素。

## 时间线复盘（事故复盘模板）

```
T-30min  监控看到 p99 异常
T-29min  oncall 收到页面，进入战时频道
T-25min  定位到下游服务 X
T-20min  发现 X 在 18:00 发过 release
T-15min  revert X 的 release
T-10min  监控回到基线
T-5min   灰度开启
T0       全量恢复，写复盘文档
```

时间线要诚实——延迟一分钟没响，记下；决策犹豫，记下。

## 修复的四个层级

1. **Mitigation（缓解）**：临时把危险关掉（关流量、回滚、限流）
2. **Fix（修复）**：让服务回到正常
3. **Defense-in-depth（纵深防御）**：加一层防相同问题再次发生（linter、测试、监控）
4. **Elimination（消除）**：从设计上让这类问题根本没法出现

只做 1+2 = 等下一次。**至少做到 3**，条件允许做到 4。

## 反模式

- "RCA = 写'操作失误'" → 把责任推到人 = 没找到根因
- "RCA 没人 review" → 写 RCA 的人和审的人**不是同一拨**，避免自审盲点
- "RCA 写完不下发" → 下发 = 让所有工程师**能在未来事故中用到**
- "RCA 无 action 项" → 没有 action 的 RCA 是日记
- "action 项没 owner / 没 deadline" → 无 owner 的 = 不做
