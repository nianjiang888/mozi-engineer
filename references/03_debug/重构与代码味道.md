# 重构与代码味道

> 重构是改善代码结构而不是改行为。任何"顺带修一下"的提交都不是重构。

## Red-Green-Refactor 的 Refactor 时段

- 重构只能在**测试保护下做**（既有覆盖率 or 临时补测试）
- 重构每次只动一种味道
- 每步跑测试，绿了再下一步

## 常见代码味道与对应动作

| 味道 | 表现 | 修法 |
|---|---|---|
| **Long Method** | 一个函数 > 30 行 | 抽 sub-function；按意图命名 |
| **God Class** | 一个类 7+ 职责 | 按职责拆分 |
| **Feature Envy** | 函数 90% 在用别的类的字段 | 挪过去 |
| **Primitive Obsession** | 满屏 string/int 当"钱/状态/单位" | 建值对象（cents 而不是 float） |
| **Shotgun Surgery** | 改一处要改 N 个文件 | 把改动点收敛到一个抽象 |
| **Divergent Change** | 一个类因为不同原因被改 | 拆，按变更原因切 |
| **Data Clumps** | 3 个字段总是一起出没 | 建对象包它们 |
| **Speculative Generality** | "以后可能用得上"的抽象 | 删；真用上时再加 |
| **Duplicate Code** | 3 处以上的复制粘贴 | 抽函数；不要给参数 hack |
| **Dead Code** | 没人调用 | 删 |

## 重构的"四件套"

1. **先备份**：branch + commit
2. **写一个能稳定失败的测试**：覆盖当前行为
3. **做小步重构**：提取常量 → 提取函数 → 移动 → 拆类
4. **每步跑测试**：绿了再下一步

## 重构与改行为的边界

| 重构 | 改行为 |
|---|---|
| 抽函数，函数名换 | "顺便加个缓存" |
| 改命名更准确 | "顺便修这个 bug" |
| 拆类，行为不变 | "顺手加个新参数" |

**别同时做**。 改 PR 拆开提交。

## 何时不重构

- 写代码没写过 → 第一次"乱"是对的，先跑起来
- 没有测试保护 → 重构前补测试
- 还在高速迭代新需求 → 留 issue，等稳定期再做

## 工具支持

- 自动重构：IDE 重构工具（重命名、提取、移动、提取接口）
- 静态分析：SonarQube / CodeQL / Semgrep
- 测试守护：覆盖率基线，不许降

## 反模式

- "一次性重构整个模块" → 拆 5 个 PR，每个独立合并
- "重构和修 bug 一起合" → 一个 PR 一个意图
- "重构完没跑测试就合" → 重构是结构变化，行为必须零回归
- "重构靠注释解释" → 别解释坏代码，重构它
