# 事故复盘

> 事故不写复盘 = 同样的错再来一次。复盘不是为了追责，是为了**让下次发生能恢复得更快**。

## 复盘的四个目标

1. **写时间线**：客观时序（事实，不是解读）
2. **找根因**：机制层，不是"操作失误"
3. **派 action 项**：每个 owner + deadline
4. **分享给团队**：其他人能避免同样的坑

## 复盘的两个时间窗

| 立即复盘（24h 内） | 完整复盘（1-2 周内） |
|---|---|
| 时序 + 缓解 + 关键节点 | 根因 + 流程改进 + 监控/测试/设计反馈 |

## 写时间线（不带评价）

```
[症状]    10:32  监控报警订单成功率 < 95%
[响应]    10:33  oncall 看到报警
[响应]    10:35  oncall 进入战时频道
[发现]    10:40  定位到下游支付服务 X 报错
[假设]    10:45  怀疑 X 的 release 导致
[动作]    10:48  revert X 的 release
[恢复]    10:55  监控回到基线
[收尾]    11:00  oncall 把流量切回主链路
```

**不要写**：操作员这时候在喝水、某某反应慢。**只写事实**。

## 找根因（Five Whys / 鱼骨图）

跑"为什么会发生"直到答案落**机制/流程/设计/数据**层，**不落人**层。

```
症状    : 订单成功率掉到 80%
为什么  : 支付服务 X 报错
为什么  : X 在 18:00 release 后证书过期
为什么  : release 流程没强制检查证书有效期
为什么  : 我们没用 release checklist
```

根因 = **release 流程缺少证书校验 checklist**。修法 = checklist 加这一条 + CI 强制。

## Action 项（必须有 owner 和 deadline）

```
A1: 在 release checklist 加证书有效期检查
   owner: 莉莉
   deadline: 2 周内
   acceptance: CI 强制，错过 merge 失败

A2: 告警规则加"证书 < 14 天过期"通知
   owner: 王五
   deadline: 1 周内
   acceptance: Prometheus 规则部署并测试报警
```

**没有 owner 没 deadline 的 action = 不做**。每一条都过这一关。

## 哪些是"贡献因素"不是"根因"

- 当时是不是半夜（人手少）→ 贡献因素
- oncall 是新人 → 贡献因素
- 没监控 → 贡献因素
- 上游有 release → 贡献因素

**根因只能一条**（去掉这一条事故就不会发生），贡献因素 N 条。

## 复盘文档的下发

- 文档短（1-2 页足够），核心读者：未来会 oncall 的同事
- 公开（团队内），不是批斗任何人
- 不要到全员群里"@所有人" → 灌水会让人麻木
- 进"事故集"(postmortem archive)，按子系统索引

## 没有事故文化的组织怎么做

- 写复盘 = **承认这次错，不是认这个人**
- 复盘会 = 听意见会，不是审判会
- oncall 出错是组织问题不是个人问题 → 培养机制，不是惩罚
- 老板也认领过错 = 复盘真有文化

## 反模式

- "操作员手快按错了" → 把责任推人
- "业务侧催得急所以跳过了流程" → 业务催是常事，流程要 hold
- "复盘只有当事人看" → 复盘要下发 = 写到大家能找的地方
- "action 项没 track" → 没有 dashboard = 没做
- "半年不解决" → 重复事故 = 之前复盘没闭环
