# 生产就绪

> 能跑 + 能测 + 能回滚 + 能看清 = 生产就绪。

## 上线清单（每个 PR 都要过）

### 必须（不过不许合并）
- [ ] Spec 链接 + 验收条件勾上
- [ ] 测试：单元 + 集成 +（关键路径）E2E
- [ ] 静态检查：linter + format
- [ ] 依赖：lockfile 已更新
- [ ] 监控：新增指标 / 告警已配
- [ ] 文档：CHANGELOG / Runbook 已更新
- [ ] 灰度策略：百分比 / 名单 / 灰度维度

### 推荐
- [ ] 性能 baseline（p50/p95/p99，对比上一版）
- [ ] oncall 演练过这个改动
- [ ] BDDF 演练过一次（业务降级方案）

## 上线的三种姿势

| 姿势 | 适用场景 | 反例 |
|---|---|---|
| 直接部署 | 无状态、低风险 | 直接改涉及钱的代码 |
| 灰度（金丝雀）| 中风险 / 影响范围大 | 全量一刀切到核心路径 |
| feature flag | 业务开关 + 可即时回滚 | 改完发版本等了用户 |

## 可观测性的三大支柱

- **Metrics（指标）**：RED（Rate/Errors/Duration）+ USE（Utilization/Saturation/Errors）
- **Logs（日志）**：结构化 JSON，每条带 trace_id；不要打敏感数据
- **Traces（链路追踪）**：跨服务调用能 join；采样率按场景调整

## 几个常用指标

```
请求级别：
  http_requests_total{method, route, status}
  http_request_duration_seconds_bucket{...,le="0.05,0.1,0.5,1.0"}
  http_request_errors_total{...,reason="timeout|4xx|5xx"}

依赖级别：
  db_pool_active, db_pool_idle
  cache_hit_total, cache_miss_total
  upstream_response_seconds_bucket{upstream}

业务级别：
  orders_paid_total, order_amount_total
  payment_errors_total{reason}
```

## 告警的"反金字塔"

不要把"机器心跳"当告警，告警要**可触发 oncall 动作**：

- ✅ "订单成功率 < 99% 持续 5 分钟"
- ❌ "CPU > 80%"（多半 CPU 高没问题）

告警 = **可行动**的告警。

## SLO（服务水平目标）

每月 SLO 算 burn rate：

```
月度 SLO 99.9% = 43 分钟错误预算
5 分钟 14x burn rate → 立刻报警
1 小时 6x burn rate → 1h 内跟进
```

## 灰度策略

| 维度 | 适用 |
|---|---|
| 比例 | 1% → 5% → 25% → 100% |
| 用户 | 内部 / 白名单 / 灰度名单 |
| 城市 | 单城市验证 → 全国 |
| 时段 | 低峰 → 高峰（要慎重）|

灰度期间盯 5 个东西：成功率、延迟、错误率、用户反馈、核心业务指标。任何一个跑偏立刻回滚。

## 回滚

- 必须 30 秒内能回滚 = 一个命令
- DB 迁移**前向兼容**（加列允许 NULL；不要 drop）
- 旧版本仍能跑最新库

## 反模式

- "上线完立刻走" → 24h 重点观察期
- "告警全开 = 安全" → 告警疲劳 = oncall 屏蔽 = 真告警也漏
- "指标全收" → 存储费 + 数据噪音，只留有用的
- "回滚 = 再发一版" → 必须能 revert，forward fix 不是回滚
